# Architecture decisions

Format: one entry per decision — Context / Options / Outcome / Recommendation. Newest at the bottom.

## D-001 — Sprint 0 scaffold choices (2026-09-24)
**Context.** First code in the repo; the choices here shape every later sprint.

**Outcome.**
- Package manager **pnpm 12**; frontend **Svelte 5 (runes) + TypeScript + Vite 8**; Tauri **2.11**; Rust stable.
- App identifier `com.checkflat.app`, product name `Checkflat`. Rust lib crate name `checkflat_lib`.
- **Cargo workspace at the repo root** (`src-tauri`, `spikes/report-spike`) so spikes and the app share one `target/` and one dependency graph. Consequence: build artifacts live under `target/`, not `src-tauri/target/` (CI paths depend on this).
- `src-tauri/gen/android` (generated by `tauri android init`) **is committed**, as Tauri intends; its `build/`, `.gradle/`, `local.properties` are ignored.
- Windows bundle: **NSIS only**, `installMode: currentUser` (no admin rights needed on the client's laptop).
- Release profile: `opt-level = "z"`, LTO, `codegen-units = 1`, `panic = "abort"`, `strip = true` — size matters more than speed for an APK (`z` vs `s` measured in D-004: −6 % size, +20 % render time on a 20 ms render).
- Dev profile: `debug = "line-tables-only"` for our crates and no debug info for dependencies; otherwise the debug `.so` with Typst is ~180 MB.
- **Client data is never committed.** `Examples/` and `public/spike/` are gitignored; `scripts/copy-spike-plan.sh` copies the A1 plan locally; the viewer degrades to "no spike plan bundled".
- PDF.js runtime assets (`cmaps`, `standard_fonts`, `wasm`, `iccs`) are copied from `node_modules` into `public/pdfjs/` by `scripts/copy-pdfjs-assets.mjs` on install/dev/build and are gitignored.
- CSP allows `worker-src blob:`, `wasm-unsafe-eval` and `img-src data: blob:` for PDF.js.

## D-002 — Spike A: A1 plan viewing with PDF.js on Android (2026-09-24)
**Context.** Risk "A1 plans → lag on phone" (plan §6). Test asset: the client's real A1 plan `c-JS00-AM01.pdf` (2384×1684 pt = 841×594 mm, 1 page, 2.9 MB, raster-heavy, 15 embedded images). Devices: `Phone_API35` (pixel_8, 1080×2400, DPR 2.625) and `Tablet_API35` (pixel_tablet, 2560×1600, DPR 2), both Android 15 with **WebView 124.0.6367.219**. Emulator numbers on an M4 Pro host are indicative only.

**Options.**
1. Render the whole page at the current zoom — at 8× fit on the phone that is ~33k×23k px; impossible.
2. **Capped base render + viewport tile** (chosen): render once into a canvas capped at 4096 px on the long side, pan/zoom by CSS transform only, and when the zoom exceeds the base resolution render just the visible viewport at device resolution after the gesture settles (150 ms). The base stays underneath so nothing goes blank; in-flight renders are cancelled.
3. Pre-rendered tile pyramid — more code, more memory, not needed given the results below.

**Outcome.**
- **pdfjs-dist 6.3 modern build fails on WebView 124** (`URL.parse is not a function`; `URL.parse` is Chrome 126+). Switched to `pdfjs-dist/legacy/build/pdf.mjs` + legacy worker. Keep the legacy build until the minimum WebView is known from real devices (Play-updated WebViews are ≥ 130 today, but the emulator image shows the floor is real).
- `cmaps`, `standard_fonts`, `wasm`, `iccs` are copied to `public/pdfjs/` and passed via `cMapUrl`/`standardFontDataUrl`/`wasmUrl`/`iccUrl`.

| measurement | phone (pixel_8) | tablet (pixel_tablet) |
|---|---|---|
| fetch 2.8 MB from bundle | 25 ms | 33 ms |
| base render 4096×2893 (45 MB RGBA) | 2410 ms | 2186 ms |
| time to first render (fetch+parse+base) | 2615 ms | 2413 ms |
| 4× tile | not needed (base ≥ screen px up to ~5×) | 2560×1494 px, 115–151 ms |
| 8× tile | 824×1586 px, 129–186 ms (first 163 ms) | 2560×1494 px, 128–311 ms |
| JS heap after base | 51 MB | 43 MB |
| app process PSS idle / at 8× | 146 MB / 146–153 MB | 127 MB / 201 MB |
| pan at 8× | CSS transform only, no re-render, smooth | same |

- The tile is DPR-capped at 2, so the phone renders 824×1586 tiles instead of 1080×2080; text at 8× is crisp on both.
- Memory headroom is fine: the base canvas (45 MB) is the dominant cost and fixed; tiles are screen-sized (≤ 15 MB).
- Not measured on hardware yet — see D-006.

**Recommendation.** Keep option 2 as the Sprint 2 viewer design: `MAX_BASE_PX = 4096`, DPR cap 2, viewport tile above base resolution, PDF.js legacy build. Revisit only if a real low-end phone shows the 2.4 s first render or the 45 MB base as a problem (then drop the cap to 3072 or render the base progressively). Pinch-zoom gesture code (`src/lib/gestures.ts`) exists but was exercised with wheel/mouse on desktop and with the on-screen zoom buttons on the emulators; adb cannot synthesise two-finger gestures, so real pinch is part of the D-006 device check.

## D-003 — Spike B: camera capture on Android (2026-09-24)
**Context.** Risk "Camera capture in Android WebView" (plan §6). Photos are the core of every observation.

**Options.**
1. `<input type="file" accept="image/*" capture="environment">` in the WebView.
2. Own minimal Tauri mobile plugin (Kotlin) firing `MediaStore.ACTION_IMAGE_CAPTURE`.
3. Community crate `tauri-plugin-camera` 0.1.4 (Android only, early version).

**Outcome.**
- Option 1 on WebView 124 / Android 15: the input opens the **Android Photo Picker** (`PhotoPickerGetContentActivity`), not the camera. The `capture` attribute is ignored by the Tauri/wry file chooser. Unusable for field capture.
- Option 2 (`src-tauri/plugins/camera-capture`, ~60 lines of Kotlin + the standard plugin shell): opens the system camera app directly, writes the JPEG to `cacheDir/captures/IMG_<timestamp>.jpg` via the app's existing `FileProvider` (the Tauri Android template already declares `<applicationId>.fileprovider` with `cache-path "."`), and resolves with the path. The Rust command `capture_photo` reads the file (proves Rust owns the bytes). Verified on the phone emulator (virtual-scene camera): capture → confirm → 62 KB JPEG shown in the app.
- Two Android gotchas, both hit during the spike:
  - **Do not declare `android.permission.CAMERA`.** `ACTION_IMAGE_CAPTURE` needs no permission; declaring it without a runtime grant makes the intent throw `SecurityException`.
  - **Package visibility (Android 11+):** `intent.resolveActivity()` returns null unless the manifest has `<queries><intent><action android:name="android.media.action.IMAGE_CAPTURE"/></intent></queries>`. The plugin declares it and also catches `ActivityNotFoundException`.
- The mobile plugin call blocks until the camera returns, so the Tauri command is `async` (thread pool), never on the main thread.
- Option 3 not tried: our own plugin is smaller than reading someone else's and gives control over file location and EXIF later.

**Recommendation.** Ship option 2. In Sprint 3 extend it with: gallery pick (`ACTION_GET_CONTENT` / Photo Picker — that is what option 1 already gives for free), moving the file from cache to the project's photo dir, and EXIF date read in Rust (`image`/`kamadak-exif`). On Windows the same UI falls back to a file picker (the plugin returns `Unsupported` on desktop).

## D-004 — Spike C: report engine, embedded Typst vs printpdf (2026-09-24)
**Context.** The report (M9) is the deliverable of every visit: cover + one block per observation, EN/PT, images, later a summary table. Plan §3 left the choice between embedding Typst and using printpdf to this spike. Both engines render the same one-page sample (bold title with PT diacritics, 1200×900 JPEG at 120 mm, 6-line paragraph, status box, footer) from `spikes/report-spike`, with the same Liberation Sans TTFs embedded, behind Cargo features so each can be linked alone.

**Options.**
1. **Typst** via `typst-as-lib` 0.16 (typst 0.15): template in `assets/report.typ`, data through `sys.inputs`, image through a static file resolver, `typst_pdf::pdf`. Typst does layout (justification, line breaking, figures, page footers, tables later).
2. **printpdf** 0.12 (`default-features = false, features = ["jpeg"]`): every position is computed by hand; line breaking written for the spike from the font's advance widths (`printpdf_engine.rs::wrap`), no justification, no hyphenation. Its default `html` feature (an HTML/CSS layout engine) was left off — with it the crate is far heavier than Typst.

**Outcome.** Host = M4 Pro; emulator = arm64 Android 15 debug build (unoptimized, so the ms are only comparable to each other).

| measurement | Typst | printpdf |
|---|---|---|
| output PDF (same content) | **97,836 B** | 477,604 B (fonts embedded whole, subsetting flag ignored) |
| fonts in PDF | subset, CID TrueType | full TTFs, not subset |
| render, host release | 18 ms | 51 ms |
| render, phone emulator (debug) | 289 ms | 414 ms |
| render, tablet emulator (debug) | 496 ms | 600 ms |
| clean release build of the spike crate | 53 s | 30 s |
| incremental rebuild | 2 s | 1 s |
| release APK, arm64-v8a only, only this engine | 36.4 MB (34.2 MB with opt-level z) | 11.8 MB |
| layout code written | 30-line `.typ` template | ~150 lines of Rust for the same page, still left-aligned |
| PT diacritics, justification, page footer | all correct | diacritics correct; justification/hyphenation would need writing |
| unit test (`%PDF` header, non-empty) | pass | pass |

APK sizes — **per-ABI, arm64-v8a only** (`--target aarch64`; each APK verified to contain only `lib/arm64-v8a/`), release profile, unsigned, measured locally with the same commands CI runs:

| variant | profile | APK | `libcheckflat_lib.so` |
|---|---|---|---|
| both engines | opt-level s | 39,459,971 B (37.6 MB) | 36,853,928 B |
| typst only | opt-level s | 38,202,435 B (36.4 MB) | 35,596,400 B |
| printpdf only | opt-level s | 12,389,399 B (11.8 MB) | 9,783,360 B |
| **typst only** | **opt-level z** | **35,810,083 B (34.2 MB)** | **33,204,048 B** |

Release profile experiment (typst only, arm64): `opt-level = "s"` → `"z"` with `lto = true`, `codegen-units = 1`, `strip = true`, `panic = "abort"` unchanged (they were already set) saves **2,392,352 B (−6.3 %)** on the `.so` and the APK; host render time goes from 18 → 22 ms (Typst) and 51 → 63 ms (printpdf); the local release build took 103 s instead of 82 s. `opt-level = "z"` is now the workspace release profile (D-001).

CI (ubuntu-latest, same SDK/NDK versions, opt-level z, run 36032448873) measured the same variants slightly smaller than the macOS host, presumably from the Linux-hosted NDK linker: both 36,001,851 B (34.3 MB), typst only 34,753,803 B (33.1 MB), printpdf only 11,071,655 B (10.6 MB); the installable debug APK with both engines is 174.8 MB.

So **Typst costs ~22–24 MB of APK** on top of the ~11 MB Tauri shell + printpdf baseline.

**Recommendation.** **Embedded Typst**, accepting the ~26 MB APK cost. Reasons: render time and PDF size are better (5× smaller reports matter when they are shared from a phone), and — the decisive point — the whole report layout (Aproplan-like blocks, summary table, EN/PT strings, page numbers, later a table of open items) becomes a 30-line template instead of hand-placed operators with hand-written line breaking; every layout change in Sprints 5–8 would otherwise be Rust geometry code. A 38 MB single-user field app is well inside what the client's Android phone and Windows laptop tolerate. Two mitigations to try in Sprint 5 before accepting the full delta: depend on `typst` + `typst-pdf` directly instead of `typst-as-lib` (which also pulls `typst-html` and `typst-svg`), and check what `opt-level = "z"` saves. If the delta cannot be brought under ~15 MB **and** the client objects to the download size, printpdf remains viable: the spike shows the layout work is feasible, just manual (`printpdf_engine.rs`), and the `report-spike` feature split shows how to swap. Other Sprint 5 follow-ups: Typst `lang: "pt"` hyphenation, a font with wider coverage if client logos/texts need it, and image downscaling in Rust before embedding (the `image` crate, plan §3).

## D-005 — CI layout (2026-09-24)
**Context.** Dev machine is macOS; Windows and Android builds must come from CI. Spike C needs APK size per report engine.

**Outcome.** `.github/workflows/ci.yml`:
- Triggers: push to `main`, pull requests, `workflow_dispatch`; `paths-ignore` for `docs/**` and `**/*.md`; concurrency group per ref with cancel-in-progress.
- `android` job (ubuntu): Temurin 21, `android-actions/setup-android` (platform 35, build-tools 35, NDK 27.2), `aarch64-linux-android` target, `pnpm tauri android build --debug --apk --target aarch64` three times (default = both engines, `--features report-typst`, `--features report-printpdf`, the last two with `--no-default-features`); APK sizes printed to the job summary; APKs uploaded as `android-debug-apks`.
- `windows` job: `cargo test -p report-spike --features typst,printpdf`, then `pnpm tauri build --bundles nsis`; uploads `target/release/bundle/nsis/*.exe` as `windows-nsis`.
- Caches: `Swatinem/rust-cache` on the workspace root, pnpm store via `actions/setup-node`.
- Debug APKs use the default debug keystore; no signing secrets in Sprint 0.
- Engine variants: the app crate has no default engine features; `tauri.conf.json` `build.features` lists both, and CI overrides it per variant with `-c '{"build":{"features":[...]}}'` because the Tauri CLI has no `--no-default-features`.

**Status (2026-09-24).** The first runs were refused by GitHub ("recent account payments have failed or your spending limit needs to be increased" — Actions minutes on a private repo are billed). After the repo was made public, run 36032448873 was **green on both jobs**: Android 19 min (debug APK + three release variants), Windows 19.5 min (tests + NSIS installer, artifact `windows-nsis` 11 MB zipped). The three release size builds were then moved into a separate `android-size` job that runs only on `workflow_dispatch`, so push/PR runs build just the debug APK and the NSIS installer.

## D-008 — Migrations: rusqlite_migration on `PRAGMA user_version`, backup before migrating (2026-09-25)
**Context.** Sprint 1 introduces the SQLite schema that every later sprint extends; migrations must be safe on a phone with no way to recover a broken database.

**Options.** Hand-rolled `user_version` loop (~40 lines); **rusqlite_migration** (small, no macros, `user_version`-based, `validate()` for tests); refinery/sqlx (table-based tracking, heavier).

**Outcome.** rusqlite_migration 2.6: `Migrations::new(vec![M::up(SQL_V1)])`, `to_latest`; `validate()` runs in a unit test. Migration 1 creates all v1 tables (`project`, `plan`, `visit`, `observation`, `photo`, `setting`). Before migrating a database with `0 < user_version < latest`, `apply_with` runs `PRAGMA wal_checkpoint(TRUNCATE)` and `VACUUM INTO '<db>.bak-v<old>'` — a consistent copy independent of WAL state (unlike `fs::copy` of an open file). Fresh and up-to-date databases are never copied; backups are not auto-deleted. `db::open` returns `freshly_created` so callers can distinguish a new database from an existing one. Connection setup: `foreign_keys = ON`, `journal_mode = WAL`, `busy_timeout = 5000`, `synchronous = NORMAL`. Tests: fresh DB, idempotent reopen, backup content and overwrite, validate.

## D-009 — UUID v7 ids and RFC 3339 UTC timestamps (2026-09-25)
**Outcome.** All primary keys are `TEXT` UUID v7 (`uuid` crate, `Uuid::now_v7()`): time-ordered, globally unique, so archives (M10) and any future sync can merge rows from two devices without renumbering. Timestamps are `TEXT` RFC 3339 UTC with millisecond precision and a `Z` suffix (`time` crate, `clock::now_iso`), lexicographically sortable. Additions to the plan's data model: `created_at` on every table, `updated_at` on `project`/`observation`, `UNIQUE (project_id, ref_no)`, `CHECK` on `x_norm`/`y_norm` (0..1) and `report_lang` (en|pt), and a per-device `setting` table. `project.next_ref_no` keeps continuous-per-project numbering configurable until the client confirms.

## D-010 — File layout, relative paths, delete order, quarantine sweep (2026-09-25)
**Outcome.**
- The database stores only paths relative to the app data dir (`RelPath`): `projects/<project_id>/plans/<plan_id>.pdf`, later `photos/<photo_id>.jpg` and `logo.<ext>`; `tmp/<token>.pdf` for import staging; `projects/.trash/` for quarantine; `checkflat.db` (+ `-wal`, `-shm`, `.bak-v<n>`) at the root. Validation is string-based and identical on every OS (rejects leading `/`, `\\`, `:`, control characters, empty/`.`/`..` components) because `Path::is_absolute` differs per platform; `resolve()` asserts the result stays under the data dir.
- Deleting a project deletes the row first (cascade), then `projects/<id>/`; a failed disk removal can never leave a row pointing at nothing.
- `sweep_orphans` at startup **quarantines instead of deleting**: unknown UUID-named project dirs and unreferenced files under live projects' `plans/`, `photos/`, `logo.*` move to `projects/.trash/`; staging files older than 24 h and quarantine entries older than 7 days are removed. Containment: only UUID-named entries, symlinks never followed, every path canonicalized under the data dir, references compared case-insensitively on Windows. **Skipped entirely when the database was created in this run** — an empty database after a lost/replaced file must never wipe user files.
- **Sprint 8 notes:** run `PRAGMA wal_checkpoint(TRUNCATE)` before exporting/copying the database so `checkflat.db` alone is complete; the `setting` table is per-device and is excluded from archive export and never overwritten on import.

## D-011 — PDF page size read in Rust with lopdf (2026-09-25)
**Options.** PDF.js in the WebView (already the renderer) vs **lopdf** in Rust.

**Outcome.** lopdf 0.45 (`default-features = false`): page count, MediaBox of page 1 with `/Parent` inheritance, `/Rotate` 90/270 swaps width/height, CropBox fallback; values rounded to 0.001 pt. Import is then one Rust transaction (stage → inspect → rename → insert), unit-testable, identical on Android and Windows, and reusable by the archive import without a WebView. Verified locally on the client's three plans (A1 2384×1684 pt; two A4 sheets 841.89×595.28 pt). PDF.js stays the renderer; Sprint 2 cross-checks its page size against the stored one.

## D-012 — i18n: shared JSON, tiny helper, language in the `setting` table (2026-09-25)
**Outcome.** `i18n/en.json` and `i18n/pt.json` at the repo root are the single source of strings: the UI imports them (`src/lib/i18n.svelte.ts`, ~40 lines, `{name}` interpolation, English fallback, then the key itself) and `checkflat-core::i18n` `include_str!`s the same files for the Rust report later; a unit test enforces identical key sets and placeholders in both languages. No svelte-i18n: ICU plural rules are not needed in v1 and the files must stay trivially parseable from Rust. The chosen language is persisted in `setting` (`language` = `en`|`pt`) and read at startup; default from `navigator.language`.

## D-013 — Plan import rules and the camera plugin as Android bridge (2026-09-25)
**Outcome.**
- **Multi-page PDFs are rejected** at staging (`multi_page` error with the page count); the client works with one plan per file. Page selection can be added later.
- Import is two commands so the source is read **once** and the user confirms an editable title first: `stage_plan_source` (fs plugin `open` — resolves `content://` on Android through the ContentResolver — streamed into `tmp/<token>.pdf`, inspected) then `import_plan` (atomic rename into the project + insert) or `discard_staged_plan`.
- **Display name on Android** comes from a `displayName` command added to the existing Kotlin plugin (`OpenableColumns.DISPLAY_NAME` on a background thread, sanitized); desktop uses the file name. The plugin now acts as the app's Android bridge; renaming it is a later, separate change.
- `observation.plan_id` uses the composite FK `(plan_id, project_id) → plan(id, project_id)` with the default **`NO ACTION`**, not `RESTRICT`: RESTRICT is checked immediately per row and could make a project delete fail depending on cascade order, NO ACTION is checked at statement end (sqlite.org/foreignkeys.html §4.3). The app refuses to delete a plan that has observations (`plan_has_observations`); the FK is the safety net; the composite key also guarantees plan and observation belong to the same project.
- **Command threading rule:** every command is `async`, awaits (fs open, plugin calls) come first, then DB/disk work runs in `spawn_blocking` holding the `std::sync::Mutex<Connection>` — a guard can never live across an `.await` (it is not `Send`); poisoned locks are recovered.
